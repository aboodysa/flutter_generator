# FLUTTER_TOOLCHAIN — the declared toolchain floor (S-HERMETIC, closes C12)

> Source: `SPIKE_S_HERMETIC_REPORT.md` (§13 D1/D2, §14), ratified in
> `S_HERMETIC_IMPL_BRIEF_CLAUDE.md`. This doc is the single reference for "what toolchain does a
> generated app build against" — linked from `DESIGN.md` §23 and `DETERMINISM_CONTRACT.md` §5.

## 1. Installed toolchain (ground truth)

Captured by the SwiftUI spike's tooling census, reused here for the Flutter path
(`SWIFTUI_GROUND_TRUTH.md:91-93`):

```
$ flutter --version
Flutter 3.44.3 • channel stable • https://github.com/flutter/flutter.git
Tools • Dart 3.12.2 • DevTools 2.57.0
```

No `fvm`, `.tool-versions`, `.flutter-version`, or CI workflow exists in this repo (Flutter runs
on the Mac, not in CI) — this doc plus the `[lockfile]` validate gate are the enforcement seam,
not a pinned toolchain manager. **Re-verify with `flutter --version` on any new build machine**
before regenerating or building an app; a mismatch against the floor below is the signal to
update, not silently proceed.

## 2. Declared floor (what generated code targets)

The generated `pubspec.yaml`'s `environment.sdk` and the `[lockfile]` validate gate both read
from one shared constant — `builder/src/toolchain.ts` — so the two can never drift the way the
old `sdk: ^3.0.0` and every committed lock's proven `dart >=3.11.0` did:

| | Value | Source |
|---|---|---|
| `DART_SDK_FLOOR` | `>=3.11.0 <4.0.0` | `builder/src/toolchain.ts` — the floor every committed `pubspec.lock`'s `sdks:` block already proves (§3) |
| `FLUTTER_SDK_FLOOR` | `>=3.38.4` | `builder/src/toolchain.ts` — same provenance |

The floor is deliberately the *proven minimum*, not the *installed* version (§1) — a caret-range
dependency tree resolves against the floor, and the installed toolchain (3.44.3/3.12.2) sits
comfortably above it. Ratified (implementation brief #1): keep caret ranges everywhere else
(D1 below); only the SDK floor itself gets tightened.

## 4. The two-layer contract (L1 / L2)

- **L1 — generator determinism**: same IR + same generator version → identical generated bytes.
  Already proven by the `[determinism]` and `[plan-determinism]` gates
  (`DETERMINISM_CONTRACT.md`). S-HERMETIC adds nothing to L1 — no wall clock, no network, no
  randomness enters generation; the committed lock is *consumed* by `pub`, not by generation.
- **L2 — build reproducibility**: same generated source + same SDK/dependency lock → an
  equivalent dependency graph and toolchain-controlled build output. **This is S-HERMETIC's
  target.** It does not promise byte-identical binaries (that would require controlling the full
  Dart/AOT/compiler environment) — only that the same lock resolves the same package versions.

## 5. Lock-refresh ceremony

Lockfiles are intended to be tracked and are (`.gitignore` does not exclude `pubspec.lock`) —
formalizing the existing de-facto state (SPIKE_S_HERMETIC_REPORT.md §12.1-12.2), not changing it.
Each natural regenerate of an app should:

```
flutter pub get && git add apps/<app>/output/app/pubspec.lock
```

(or the equivalent `builder/output/<sample>/pubspec.lock` path for a sample) so the commit stays
coherent — the generated `pubspec.yaml` and its resolved lock land in the same commit, keeping
`[lockfile]` a reviewable diff instead of an invisible drift. This is a documented convention, not
new tooling (SPIKE_S_HERMETIC_REPORT.md §15 rejected a CI-enforced pin — no CI exists in-repo and
Flutter runs on the Mac).

## 6. C12 closure

**C12 ("byte-identical broken by toolchain, not the selector") is CLOSED via S-HERMETIC:**
commit-lockfile-per-app is ratified policy (§5); the SDK floor is ratified at `>=3.11.0 <4.0.0`
dart / `>=3.38.4` flutter (§2), tightened in the generated `pubspec.yaml` and enforced by the
`[lockfile]` validate gate; the toolchain record is ratified at `SWIFTUI_GROUND_TRUTH.md` §1.5
(§1) and now has a Flutter-specific home (this doc). See `SPIKE_PLAN.md`'s decision log (C12 row)
for the roadmap-level closure entry.
